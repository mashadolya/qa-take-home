Optional form section: dependent data not cleaned up on edit

Maryia Dolia · Senior QA take-home · Product A (B2B SaaS for professional & financial-services firms), mobile app · Nov 2023 – May 2024 · test & pre-prod environments

1. What happened

Role: Lead QA Automation Engineer (Mobile) on Product A: led mobile test automation, built the framework from scratch with Appium and WebdriverIO for iOS and Android, mentored 2 automation engineers. Stack: React Native client (iOS and Android), REST backend, relational DB plus a separate image storage service; QA: TypeScript, Appium, WebdriverIO, Jest, Jenkins, Fastlane, Allure, AWS.

Feature: a form with base fields and an “Add additional details” checkbox that reveals an extra section with its own fields and images. The spec described create and display but said nothing about what happens to the section’s data when it is switched off later.

Trigger: while testing edit scenarios I created a form with the section and images, edited it, unticked the box and saved. The UI looked correct (section hidden, “Saved”), but I took the section image URLs from the app’s traffic (proxy) and opened them directly: they were still served. They stayed in storage, and the user could still reach them. That is BUG-001. On the test environment I also found BUG-002: a user ticks the box, types into the section, unticks it and saves. The hidden values were still sent, so the user got a validation error on a field they could not see and had no way to understand it.

Why it escaped earlier checks: nothing was visible at UI level, and mobile regression checked only what the screens showed. The DB did not cascade into a separate storage service, and with no acceptance criterion for “switching off” nobody tested it.

What I did: reproduced both bugs through the proxy log and the API, and logged them with evidence. I raised the spec gap with the PO, which produced a new criterion: disabling the section deletes its fields and images on save; cancel keeps them. I added API checks and the edit/cancel UI cases to regression. Outcome: both fixed before production (caught on test/pre-prod, no customer exposure). The new acceptance criterion became part of the story, and the API checks and edit/cancel cases stayed in regression.

3. Real defect from the incident

BUG-001Images of “Additional details” remain in storage and are reachable by URL after the section is disabled
Env / SeverityTest & pre-prod, React Native app on iOS and Android (reproduced on both). Major (data retention / privacy, silent; no UI symptom), Priority Medium
Steps1) Create a form, tick “Add additional details”, fill the fields, upload an image, Save. 2) Copy the image URL from the traffic (proxy). 3) Edit → untick → Save. 4) Open the copied URL. 5) Tick the box again, fill the section, Save.
ExpectedAfter 3) the section fields and images are deleted. 4) returns 404. 5) shows only the new data, no old images.
Actual4) 200, image served. Images and section values still stored; 5) the old images come back in the section.
EvidenceThen: proxy log with 200 for the image after save; API response; storage record. Reproduced on the stand-in: docs/evidence/bug-001-*.png, bug-002-*.png
LinkedBUG-002 (Medium): hidden section values were sent on save after unticking, causing a validation error on an invisible field

4. API / data

REST: POST/GET/PATCH/DELETE /api/forms/:id, POST /api/forms/:id/images, GET /images/:id. Checked: status codes, details null/empty, image URL reachability, validation error field.

SQL (data mattered, because orphans are invisible to the UI):

SELECT COUNT(*) FROM stored_images
 WHERE form_id = :id AND section = 'details'; -- 0
SELECT has_details, reference_code, details_note
 FROM forms WHERE id = :id; -- 0, NULL, NULL

On the real project the check was a GET request to the image URL: after the section was disabled it still returned the image (200).

5. Agile: question for PO / Eng

“When a user disables an optional section, should its data be hard-deleted on save, soft-deleted with an undo/audit retention period, or kept hidden? Does the answer change if the images were already exported or shared?”

The spec was silent, and the answer decides the expected result of every test above (404 vs. 403 vs. 200 for an admin), so I would not automate further until it is answered. The one rule I would propose upfront: before save, disabling is reversible (re-ticking restores the draft, Cancel keeps everything); only Save deletes the data.

Tools: Claude Code (Claude Opus 5.5) in the terminal for the plan, stub, tests, CI, README and this PDF draft; the playwright-cli skill to drive the running app. I ran and reviewed every step. Workflow: my review rules are saved in Claude Code project memory (braces on every if, camelCase maps, api/ db/ ui/ common/ layout, no magic values), so a correction sticks across sessions, and ESLint enforces them where it can. Prompts (condensed from the session): (1) Context + constraints, plan first. “Context: my CV, the brief and the real incident (checkbox section with fields and images; after unticking on edit the backend kept the images). Rejected / changed by me: the public sandbox (it cannot reproduce my bug); AI’s code style (one-line if, UPPER_CASE maps like API_ROUTES.FORM(id)) and its single-folder layout; I also rejected a later “flattened” version as too primitive. In code review I moved SQL out of the API steps into its own db/ layer, split actions from verifications, and swapped a format check for a plain “required” rule that shows BUG-002 more clearly. Details I did not remember exactly (fix, severity) are reconstructed from memory.

§4 AI, Part B: the original incident with today’s workflow

Delegate: a state-transition matrix from the story (toggle × save/cancel × create/edit/delete/re-enable) to find missing acceptance criteria; API client and fixture boilerplate; a SQL query for orphaned rows; triage of anonymized storage logs; first drafts of bug reports from my notes. Never without human verification: the expected behaviour (a business and privacy decision that belongs to the PO), severity, final assertions, and anything with customer data. Prompts get synthetic fixtures only: no real images, URLs or IDs.

Speed / coverage / triage: then, I found BUG-001 by hand during edit testing, after the feature was built. With the matrix in refinement, the question “what happens to the data on uncheck?” would have come up before the code was written (shift-left), and the API and SQL checks would have been ready the same day, not added after the bug.

Risk: AI writes tests from the implementation, so it treats the bug as correct behaviour (for example, asserting the images are still returned because the API returns them). Mitigation: expected results come only from criteria agreed with the PO, and every new test must be seen failing against the buggy build (the BUGS= switch / mutation) before it is merged.
